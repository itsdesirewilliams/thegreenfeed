# TheGreenFeed

A mobile-first environmental-awareness website focused on practical waste
management, built as a thoughtful extension of TheGreenFeed's Instagram
campaign. Founder and blog author: **Hannah Lepathy**.

- Instagram: [@theg.r.e.e.nfeed](https://www.instagram.com/theg.r.e.e.nfeed/)
- Stack: Next.js (App Router) · TypeScript · Tailwind CSS v4 · shadcn/ui ·
  Supabase (survey storage only)
- Deployment target: GitHub → Vercel

> **Status: Phases 1–3 implemented.** The full site (Home, About, Blog with
> four articles, Survey, 404) is built and all checks pass. The survey stays
> closed — both the UI and the submission endpoint return a clear "not yet
> available" state — until the final questions are supplied and the database
> is set up (see the manual steps below). Not deployed yet.

## Environment variables

Copy the placeholder file and fill in your own values:

```bash
cp .env.example .env.local
```

`.env.local` is git-ignored. `.env.example` contains placeholders only and is
safe to commit. Variables:

| Variable | Scope | Purpose |
| --- | --- | --- |
| `SUPABASE_URL` | server only | Supabase Project URL |
| `SUPABASE_PUBLISHABLE_KEY` | server only | Supabase publishable key (a legacy `anon` key works here if your project has not migrated) |
| `SUPABASE_SECRET_KEY` | server only | Privileged key for the survey insert route. **Never** prefix with `NEXT_PUBLIC_`. |
| `ADMIN_SESSION_SECRET` | server only | 32+ random characters; signs the admin session cookie. Required to enable the admin panel. |
| `ADMIN_PASSWORD_HASH` | server only | Preferred admin credential, `scrypt:<saltHex>:<hashHex>` (see "Admin panel"). |
| `ADMIN_PASSWORD` | server only | Fallback plaintext admin password, compared in constant time. Use only if a hash is not possible. |

These names match the Vercel project environment exactly. None is prefixed with
`NEXT_PUBLIC_`, so none is exposed to browser JavaScript; the browser never talks
to Supabase directly — submissions go through the server-side `/api/survey`
route.

Where to find the values: Supabase dashboard → **Project Settings → API**.
The site still builds and runs without these values; only the survey depends on
them.

## Supabase setup

Survey responses are stored in Supabase Postgres with a server-generated
timestamp. Blog content stays local and static; there are no blog tables.

The table is created by the version-controlled migration
`supabase/migrations/20261015000000_create_survey_submissions.sql`. It creates
`public.survey_submissions` with:

- `id uuid` — primary key, generated by the database (`gen_random_uuid()`)
- `answers jsonb not null` — the validated answers, checked to be a JSON object
- `schema_version text not null default 'v1'` — which question set produced the row
- `created_at timestamptz not null default now()` — server-generated submission time

Security is built into the migration: Row Level Security is **enabled** with
**no policies**, and all privileges are revoked from `anon` and
`authenticated`. Public visitors can neither read nor write responses; only
the server-side route handler, using the secret key, can insert.

### Applying the migration

The Supabase CLI is not configured in this repository, so the simplest path is
the dashboard:

1. Open your Supabase project → **SQL Editor**.
2. Paste the full contents of
   `supabase/migrations/20261015000000_create_survey_submissions.sql`.
3. Run it. Verify under **Table Editor** that `survey_submissions` exists and
   shows "RLS enabled" with no policies.

Alternatively, with the Supabase CLI installed and logged in:

```bash
supabase link --project-ref <your-project-ref>
supabase db push
```

Preparing the migration file (done) is separate from applying it to a project
(not done — needs the target project and your authentication). Do not consider
the table live until you have verified it in the dashboard.

## The 16-question research survey

The approved 16-question instrument (three sections: The Reality,
What Reaches You?, Make the Change) is implemented in `src/data/survey-questions.ts`.
A single student-details screen precedes the questions: full name (required),
programme / course (required), an optional phone number, and a required consent
checkbox. The 16 question/option wording is approved content — do not rewrite
the questions or invent a scoring system.

**Publication is enabled** (`SURVEY_PUBLISHED = true`), authorised by the
owner:

- `/survey` renders the live survey in production;
- `POST /api/survey` accepts validated submissions;
- the respondent must provide their name and course and tick the consent box
  before they can continue to the questions.

### How answers are stored

Each response is one row in `public.survey_submissions`:

- `answers` (JSONB) is keyed by **stable question ids** (`q1`…`q16`, plus
  `consent`, `profile_full_name`, `profile_programme`, `profile_phone`) — never
  array positions. Each research answer stores the canonical option value
  (`"a"` / `"b"` / `"c"`); the human-readable labels in
  `src/data/survey-questions.ts` act as the codebook for aggregate analysis.
  Consent is stored as `consent: true`; the student details are stored under the
  `profile_*` keys.
- `schema_version` identifies which payload the client declared. The current
  contract is `v3`; legacy `v2` submissions (no name/phone) are still accepted
  during rollout and recorded as `v2`, so rows stay distinguishable.
- `id` and `created_at` are generated by the database.

The student-details fields fit inside the existing `answers` JSONB, so **no
database migration is required** to start collecting them. Only the migration's
descriptive comment about the table (which predates personal data being
collected) is now out of date; that is cosmetic and can be updated whenever the
migration is next touched.

Because a name is collected, responses are **not anonymous**: identifying
details are stored alongside the answers and used only for TheGreenFeed's
waste-management project at PCTE.

### Pre-publication checklist

Publication may be enabled only when all of these hold:

1. All 16 questions and all 48 options are implemented (done — verify).
2. Consent and respondent-profile handling are complete (done — verify).
3. Server-side validation matches the exact schema (done — verify).
4. A valid test submission has been stored and verified in Supabase.
5. Invalid submissions are rejected server-side.
6. The complete experience has been tested on mobile and desktop.
7. The owner has reviewed the final survey and approved publication.

To enable publication afterwards: set `SURVEY_PUBLISHED = true` in
`src/data/survey-questions.ts` (nothing else needs to change; the endpoint and
page read the same flag).

### Testing locally without publishing

`SURVEY_DEV_PREVIEW=1` (development builds only) renders the survey at
`/survey` and lets `POST /api/survey` accept a submission so the full flow can
be walked through with `npm run dev`. It is ignored by production builds, so it
cannot open the survey publicly. After a test submission, verify the stored row
with:

```bash
node scripts/verify-survey-db.mjs
```

The script prints only row metadata (id, schema version, created time, total
count) — never answers or credentials.

### Notes that need attention before publication

- The programme / course dropdown options are taken from the PCTE programme
  list supplied by the owner; changing option values after publication would
  split analysis, so treat them as frozen. There is intentionally no
  class/section/batch or admission-year field (no verified source for one).
- The survey is self-reported and, because a name is collected, **not
  anonymous**; it measures awareness, message
  recall, practical knowledge, reported behaviour, campaign preferences, and
  willingness to participate as **distinct constructs** — aggregate results
  should not be merged into a single "score", and no causal claims should be
  made. Questions and options are transcribed verbatim from
  `TheGreenFeed_16_Question_Survey.md`; they must not be reworded, reordered,
  or added to.
- Approximate duration (2–3 minutes) is an estimate subject to pilot testing.
- Q5 measures prior awareness of campus fines; Q6 preserves an explicit
  "was not aware" option so awareness and perceived influence are measured as
  separate constructs.

Validation is enforced twice: in the browser for usability, and again on the
server (which is the source of truth). The server rejects consent-less
submissions, unknown keys, wrong answer types, unlisted option values,
oversized text, and payloads over 20 KB.

### Abuse protection

The endpoint currently protects itself with strict payload validation, a
20 000-character body limit, a same-origin check, and a database that only the
server-side secret key can write to. **Persistent rate limiting is not
configured, and this blocks public launch.** In-memory rate limiting would not
be reliable across serverless instances, so it was intentionally not faked.

Two supported ways to add it, in order of preference:

1. **Vercel Web Application Firewall (no code).** In the Vercel dashboard open
   the project → **Firewall** → add a rate-limit rule scoped to
   `Path equals /api/survey` with `Method equals POST`, for example
   `60 requests / 1 minute per IP`, action **Rate Limit** (HTTP 429). Platform
   rules persist across serverless instances. This is the recommended option
   because it needs no credentials in the app and cannot silently no-op.
2. **Upstash Redis (code).** Create an Upstash Redis database, then set
   `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` as Vercel environment
   variables (server-only, never `NEXT_PUBLIC_`) and add an
   `@upstash/ratelimit` sliding-window check at the top of
   `src/app/api/survey/route.ts`, returning HTTP 429 when exceeded. Do not add a
   process-local limiter.

Publication was enabled without a persistent limiter, so adding one (either
option above) remains a recommended follow-up. After launch, treat repeated
`survey_submissions` inserts as the signal to tune the limit.

## Admin panel

A small, server-rendered admin area at `/admin` lets the owner review collected
responses and the deterministic analysis without touching the database by hand.
It is **separate from the public site** and does not change the live survey.

### What it does

- **Overview** (`/admin`) — real totals, latest submission, collection period,
  instrument versions, submissions by day, and a programme/course breakdown
  (groups smaller than 5 are combined so individuals cannot be re-identified).
- **Questions** (`/admin/questions`) — per-question counts, percentages, valid N
  and missing N, with the permitted interpretation for each option.
- **Analysis** (`/admin/analysis`) — the rule-based findings: dominance,
  cross-question patterns, recommendations, and the method/thresholds/limitations
  used to reach them. Descriptive only — never a single "score" and no causal
  claims.
- **Responses** (`/admin/responses`) — a paginated list. Identifying details
  (name, phone, programme) appear only inside the protected detail view.
- **Exports** (`/admin/exports`) — on-demand CSV downloads generated server-side:
  an **aggregate** file (no names/phones) and a **raw** file (every row,
  including identifying data). Files are UTF-8 CSV with a BOM so Excel opens them
  correctly; there is no in-browser spreadsheet library.

Nothing in the admin area creates, edits or deletes rows, and every view
re-authorises the request server-side — the session cookie is never trusted on
its own.

### Enabling it

The admin area is **disabled** unless configuration is present. Set these as
environment variables (locally in `.env.local`, and in Vercel → **Project →
Settings → Environment Variables**), then redeploy:

1. `ADMIN_SESSION_SECRET` — 32+ random characters
   (e.g. `node -e "console.log(crypto.randomBytes(32).toString('hex'))"`).
2. `ADMIN_PASSWORD_HASH` — generate it locally and paste the printed value:

   ```bash
   node scripts/hash-admin-password.mjs "your password"
   # prints: scrypt:<saltHex>:<hashHex>
   ```

   (`ADMIN_PASSWORD` — a plaintext fallback, compared in constant time — also
   works, but the hash is preferred and is what the helper produces.)

No credentials are ever committed; only the variable *names* appear in
`.env.example`. If `ADMIN_SESSION_SECRET` is missing, or neither password
variable is set, `/admin` reports that sign-in is not configured and grants
no access.

### Security notes and limitations

- Access is gated by a single shared password plus a signed, HTTP-only,
  `same-site=lax`, `secure`-in-production cookie scoped to `/admin`, valid for
  8 hours. Sign-in is a Server Action, so Next.js verifies the request origin.
- Exports and every page are re-checked per request; unauthenticated API requests
  receive HTTP 401.
- Because the responses contain names and phone numbers, treat any downloaded
  file as confidential and store it in line with the consent statement and the
  project's data-protection rules.
- There is no multi-user accounts, no audit log, and no password reset. If the
  password is lost, generate a new hash and update the environment variable.
- The aggregate export never includes names, phone numbers or per-respondent
  rows; the raw export does, by design.

## Content maintenance

**Blog posts.** All four articles are typed objects in
`src/data/blog-posts.ts` — no CMS, no database. To add a post: append an
object with a unique `slug`, `title`, `summary`, `intro`, `sections`, and
`takeaway`; put its cover image in `public/images/blog/` and set
`coverImage`/`coverImageAlt`. The article route
(`/blog/[slug]`) is generated statically from that list — no other changes are
needed. Every article is attributed to `BLOG_AUTHOR` (Hannah Lepathy); do not
set `publishedAt` until a date is approved.

**Homepage carousel.** Edit the array in `src/data/instagram-posts.ts`. Each
entry has `id`, `src` (a local path under `public/`), a meaningful `alt`, and
`url`. Nothing is scraped from Instagram: images are local files, and slides
link to the profile unless an exact post URL is known. Do not fabricate post
URLs.

**Metadata.** Page titles and descriptions are set per route; article pages
also set Open Graph/Twitter data. The `metadataBase` warning during builds
disappears once a production domain is set in the root `metadata` export
(`src/app/layout.tsx`).

**One rendering note.** With Cache Components (partial prerendering) enabled,
an unknown `/blog/<slug>` renders the shared not-found UI but responds with
HTTP 200 because the static shell streams first. Known article slugs and all
other routes are unaffected; `/nope`-style top-level 404s respond with a proper
404 status.

2. **Configure credentials** in `.env.local`: `SUPABASE_URL`,

## Deployment

Deployed on Vercel at `https://thegreenfeed-p385.vercel.app`. The Vercel project
is connected to this GitHub repository, so every push to `main` produces a
Production deployment.

1. In Vercel, ensure the project's environment variables — **Project → Settings
   → Environment Variables**, for Production (and Preview if desired) — are named
   **exactly** as the application reads them:
   - `SUPABASE_URL`
   - `SUPABASE_PUBLISHABLE_KEY`
   - `SUPABASE_SECRET_KEY` (mark it as a sensitive/server-only value)
2. After changing variables, redeploy (push to `main`, or "Redeploy" in
   Vercel) so the new values take effect, then verify:
   - every route loads directly and on refresh, including `/blog/<slug>`;
   - `/survey` renders the live survey and `POST /api/survey` records a response
     (a submission missing consent should return HTTP 400, not 503).

Variable names must match exactly — a mismatch such as `NEXT_PUBLIC_SUPABASE_URL`
instead of `SUPABASE_URL` leaves the server-side Supabase client unconfigured and
submissions fail with HTTP 503 "The survey service is not configured yet".
